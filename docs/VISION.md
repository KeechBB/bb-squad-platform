## Цели (что должно уметь)

### 1. Регистрация и аккаунты

- Вход через **Steam**.
- Анкета: **имя**, **ник (только латиница)**, **возраст**, **@Telegram**, Steam ID из Steam.
- Сразу полноценный аккаунт + сессия.
- Публичный профиль (позже — со статистикой).

**Статус:** каркас v1 готов (Steam + анкета + `/profile` заглушка). В анкету ещё не добавлен **@Telegram**. Нужны деплой, Postgres.

### 2. Посещаемость тренировок (sqstat)

Источник: `https://bb.proxy.sqstat.ru/?server_id=5` (сервер Blackberry Training).

Каждый тренировочный день (МСК):

| Время | Смысл метки |
|---|---|
| **21:00** | снимок «пришёл вовремя» |
| **21:30** | снимок «был на трене» |
| после **21:30** (если зашёл только в более поздних данных / не был в 21:30) | **опоздал** |

Логика меток (зафиксировать при реализации):

- Был в снимке **21:00** → `on_time`
- Не было в 21:00, но был в **21:30** → `late_ok` («пришёл, но плохо»)
- Появился только после 21:30 / не было ни в одном снимке при известной сессии → `late` / `absent` (уточнить с капитаном)

Данные класть:

- в БД (таблица посещений по дате);
- на сайт (журнал тренировок / админка);
- в **профиль игрока** (история + сводка).

Связка игрока: ник/Steam с sqstat ↔ аккаунт на сайте (нужен маппинг ников).

**Статус:** не начато. sqstat отдаёт cookie-challenge — нужен стабильный API/парсер.

### 2b. Опрос «будешь на трене?» (Telegram-бот)

Сейчас каждый день ТГ-бот пишет клану: будешь ли на тренировке. Нужна **интеграция с сайтом**:

- кто ответил **да** / **нет** / не ответил;
- статистика ответов по дням и в профиле;
- сверка с фактом прихода (sqstat 21:00 / 21:30): обещал и пришёл / обещал и не пришёл / не обещал, но пришёл и т.д.

Связка: поле **`telegram` (@username)** при регистрации ↔ ответы бота (по username или telegram user id, если бот отдаёт id — надёжнее id).

Технически (зафиксировать при реализации):

- webhook или выгрузка из бота в API платформы; либо бот шлёт события в нашу БД;
- Keech даёт доступ к коду/токену бота или к логам ответов;
- на сайте: дашборд дня + история в профиле.

**Статус:** не начато. Нужен доступ к боту (токен / репо / формат ответов).

### 2d. Живой ростер всего клана (Telegram → файлы для агента)

Единственный полный список людей — в ТГ. Cursor в канал не добавляется.

Сделано в репо:

- бот `sostav/tg-roster-bot/` → пишет `sostav/ves-klan.json` + `ves-klan.md`
- правило: агент читает `ves-klan.md` на вопросы про весь клан
- `/seed` — первичная заливка (бот **не** выгружает всех подписчиков канала сам)
- `/add` `/del` + join/leave (если супергруппа и бот админ)

Дальше: Кич создаёт бота, кладёт токен в `.env`, один раз `/seed`, держит процесс запущенным.  
Позже — тот же поток в БД платформы / HR-кабинет.

**Статус:** каркас бота готов; ждать токен и первый `/seed` от Кича.

### 2c. Логи сервера Squad (вход/выход по Steam ID)

Цель: не только два снимка sqstat, а **точные** join/leave:

- игрок зашёл → время + Steam ID;
- вышел → время + Steam ID;
- сессия на сервере = интервал [join, leave].

Откуда брать (варианты, выбрать по доступу Кича к машине сервера):

- парсинг **логов** игрового сервера (строки connect/disconnect со SteamID64);
- либо готовый слой вроде **SquadJS** / плагины, которые шлют события на наш webhook;
- либо RCON + периодический `ListPlayers` (хуже, чем логи: можно пропустить короткий заход).

Данные → БД → профиль / посещаемость / сверка с ТГ-опросом.  
Это **точнее**, чем только 21:00/21:30; sqstat может остаться запасным или для UI онлайна.

Нужно от капитана: доступ к логам (путь/SFTP) или возможность поставить SquadJS/webhook на хост сервера.

**Статус:** идея принята, не начато.

### 3. Статистика клана (вместо только Excel)

Как сейчас скрины тренировок → Excel KDA, но:

- на сайте, все игроки BB (и опционально гости);
- фильтры: период, ник, состав Junior/Main, карта, min каток;
- отдельно от КВ-календаря.

**Рейтинг игрока (черновик формулы BB Score)** — одна шкала, прозрачная:

```
BB_Score = 1000
  + 40 * W_att      # доля тренировок с on_time (0..1) за период
  + 20 * W_lateok   # доля late_ok
  - 30 * W_late     # доля опозданий/прогулов
  + 15 * KD_norm    # нормализованный K/D за период (килы/смерти), clamp 0..2 → /2
  + 10 * REV_norm   # ресы на катку, нормализованные
  + 5  * NOK_norm   # ноки на катку
```

Период по умолчанию: **текущая половина месяца** (как Excel 01–15 / 16–конец).  
Формулу можно крутить — главное: посещаемость + стрельба, без «магии».

**Статус:** Excel уже есть; веб-таблица + рейтинг — не начато.

### 4. Кланы и команды (иерархия)

Как сказал капитан:

| Сущность | Аналогия | Пример |
|---|---|---|
| **Клан** | страна | BlackBerry |
| **Команда** | город | Main / Junior / отряд под турнир |

- У пользователя: членство в клане + опционально в одной/нескольких командах.
- Чужие кланы тоже регистрируются на платформе.
- Нужно для турниров и внутренних ивентов.

**Статус:** не начато (только User).

### 5. Профиль каждого игрока

Публичная (или для авторизованных) страница `/profile/[nick]` + свой `/profile`.

Обязательные блоки:

| Блок | Содержание |
|---|---|
| **Последние матчи** | История: КВ и тренировочные катки (дата, карта, сторона, тикеты/счёт, свои K/D/ресы/ноки если есть) |
| **Статистика** | Игровая (килы, смерти, K/D, ресы, ноки, катки) + **приходы на тренировки** (on_time / late_ok / late / absent) + **ответы ТГ-бота** (да/нет/молчал) и сводка «обещал vs пришёл» |
| **Клан и команда** | Клан («страна»), команда(ы) («город»), роли |
| **Замечания** | Предупреждения / выговоры от офицеров клана (кто выдал, дата, текст, срок/статус). Видно владельцу профиля и офицерам; публичность — настраиваемо |

**Статус:** только заглушка своего профиля без блоков выше.

### 6. Админ-панель (отдельный доступ)

Отдельный раздел сайта (`/admin`), только для ролей **platform admin** / офицеров с правами. Не путать с обычным профилем.

Возможности:

| Действие | Зачем |
|---|---|
| Редактировать **кланы** и **команды** | создание, переименование, архив, состав, роли |
| **Результаты матчей** вручную | правка / внесение КВ и тренировок (по умолчанию капитан кидает скрины агенту → импорт; админка — запасной и срочный ввод) |
| Редактировать **профили игроков** | ник, имя, возраст, привязки, замечания, ручные правки статы при ошибках |

Доступ: whitelist Steam ID / флаг `isAdmin` в БД (Keech — первый админ). Аудит: кто что менял (хотя бы лог в JOURNAL/БД позже).

**Статус:** не начато.

### 7. HR-кабинет клана (запрос главы HR)

Отдельный **вид прав: HR клана** — не platform-admin Кича и не обычный officer.

| Вид доступа | Где действует | Что может |
|---|---|---|
| **platform admin** | вся платформа | админка §6 (кланы, матчи, любые профили) |
| **officer / owner клана** | свой клан | орг-задачи, состав (уточнять) |
| **HR клана** | **только свой клан** | кабинет §7: выгрузки, identity, замечания, по матрице переключателей |

Права HR привязаны к **конкретному ClanID**: сотрудник HR клана A не видит людей/выгрузки клана B. Внутри HR — матрица флагов (п.7.5), а не одна кнопка «дать HR».

Цель: HR работает с людьми и ответами ТГ-бота, **без** статистики матчей и игрового рейтинга.

#### 7.1 Выгрузка статистики ответов боту (1 кнопка)

- Период: **настраиваемый** сотрудником HR.
- Формат CSV (или аналог):

```
ClanID | Nickname | TG_id | discord | Yes | No | Late
```

- `Yes` / `No` / `Late` — **количество** ответов «да» / «нет» / «опоздаю» в ТГ-боте за выбранный период.

#### 7.2 Выгрузка среза БД (1 кнопка → CSV)

По сути **две таблицы**:

1. **Пользователи** — все идентификационные данные людей (без матч-статы).
2. **Ответы по датам:**

```
Дата | ClanID | answer | time of answer
```

#### 7.3 Прямое редактирование идентификационных данных

HR может менять (всё **кроме** статистики матчей и прочей игровой статы):

| Поле | Примечание |
|---|---|
| имя | |
| discord | |
| telegram / TG_id | |
| Steam ID | |
| роль | |
| клан | |
| команда | |

Плюс операции вроде удаления пользователя — отдельным правом (см. 7.5).

#### 7.4 Замечания (предупреждения)

Возможность **выдавать замечания/предупреждения** пользователям (см. блок «Замечания» в профиле, п.5). Кто выдал, дата, текст, статус.

#### 7.5 Тонкие права доступа (переключатели)

Не одна роль «HR», а **матрица прав**: каждой функции — свой флаг. Примеры:

| Право | Пример |
|---|---|
| полный HR (HRD) | всё из п.7 |
| редактировать идентификационные данные | п.7.3 |
| удалять пользователей | опасное — отдельно |
| запрашивать выгрузки | п.7.1 и/или 7.2 |
| выдавать замечания | п.7.4 |

Пример: HRD = полный доступ; один сотрудник только правит данные; другой только выгрузки; третий только предупреждения.

**Статус:** требования зафиксированы от главы HR. Не начато. Зависит от: User + Clan/Team, ТГ-бот (ответы в БД), модель Warning, роли/permissions.
